## Hardware-equivalence update

The owner has now confirmed that the XBOT test controller uses the same
**G30 Gen1 3-cap hardware side** as the target 3-cap G30 controller.

This materially changes the transfer boundary. The XBOT v0.3.16 hardware result
is no longer treated as evidence from an unrelated power stage. It is now the
primary real-hardware reference for the 3-cap power-stage path.

What this does prove:
- the XBOT v0.3.16 low-level sensorless path can run a motor on this 3-cap
  hardware family
- the tested PWM/deadtime/current/BEMF/startup conventions are valid evidence
  for the same hardware side
- OPEN -> BLEND -> CLOSED is no longer merely an algorithmic reference for G30

What this does not prove:
- DeltaESC/MCSDK integration is correct
- every analogue scale/offset is identical across every 3-cap board revision
- bootloader, flash-layout, dashboard/BMS transport or configuration storage are
  identical to the XBOT firmware environment
- STAR/DELTA switching is validated

For that reason the branch remains GATE_OFF while the XBOT low-level layer is
reconciled with the DeltaESC/MCSDK execution path.

## What is transferred now

A hardware-independent handover policy is added as
`common_files/src/g30_sensorless_handover.[ch]`.

It carries the XBOT lessons that survived real hardware testing:

1. Do not hand over on one lucky observer sample. Build a saturating lock
   confidence score from repeated phase agreement.
2. Require observer/open-loop speed coherence before takeover.
3. Treat direction as an explicit, scored input and require enough evidence
   before declaring a direction fault.
4. Blend open-loop angle into observer control instead of performing a hard
   phase jump.
5. Re-check observer coherence at the end of BLEND. If it deteriorates, fall
   back to OPEN and reacquire instead of entering CLOSED blindly.
6. A stale/lost observer in CLOSED is a fault, not a reason to keep applying
   torque using an old angle.

The module has no PWM, ADC, GPIO, MOE or current-control side effects. It can be
compiled and host-tested while the G30 firmware remains physically GATE_OFF.

## XBOT facts now eligible for direct 3-cap transfer

Because the hardware side is the same 3-cap family, these XBOT v0.3.16 facts are
now valid hardware references for the G30 3-cap integration:

- PA6/PA7/PB1 BEMF_A/B/C phase-voltage channels
- coast-window BEMF sampling
- XBOT PWM/gate mapping and deadtime behavior
- current ADC polarity/order used by the working XBOT build
- the proven OPEN -> BLEND -> CLOSED timing/state machine
- the corrected forward direction convention for this hardware/motor pairing

They are still not pasted blindly into DeltaESC. Values that depend on analogue
component tolerances or control-loop rate are revalidated/scaled in the MCSDK
environment before power-stage enable:

- current ADC scale/offset
- 4 kHz XBOT timing versus the DeltaESC control rate
- 18/28/24 ADC-count current references
- 120/160-count current trips
- ~8.5% modulation ceiling
- 328 phase-step open-loop target

This distinction matters: the hardware mapping is now evidence-backed, while the
numeric tuning remains implementation-specific.

## Important PI finding

XBOT v0.3.14 fixed a real PI quantisation bug by retaining the integrator in a
fractional Q15 accumulator.

That exact bug is **not present in the SmartESC/MCSDK PI controller**. MCSDK
accumulates `hKiGain * error` in the 32-bit `wIntegralTerm` and applies the
divisor only when forming the output. Therefore the XBOT PI patch is a lesson to
verify arithmetic domains, not a patch to copy here.

## BEMF path

The previous reason for excluding the XBOT BEMF detector no longer applies:
the XBOT test controller and the G30 target share the same 3-cap hardware side.

The working XBOT PA6/PA7/PB1 phase-voltage path and short coast-window sampling
can therefore be ported as the first 3-cap sensorless anchor source. DeltaESC can
then combine that anchor with the observer/handover policy instead of inventing a
new rotor-reference path from scratch.

## Current safety boundary

This branch inherits the EBiCS/DRV126 diagnostic branch safety boundary:

- six TIM1 power-stage gate pins remain GPIO LOW
- TIM1 MOE is forced off
- configuration writes/motor setup remain blocked when firmware reports GATE_OFF
- this new handover module is not connected to the motor-control execution path

So this commit cannot turn the motor and does not weaken the existing fail-closed
state.
